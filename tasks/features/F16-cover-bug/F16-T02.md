5. **Diferenca admin vs site**: O admin serve imagens de `public/` (atualizado).

### Hipotese Chave

Se o site esta rodando em Render no mesmo server que o admin (unico servico
em `render.yaml`), entao o admin server serve TUDO. Nesse caso, a imagem
atualizada em `public/` deveria ser servida tambem para o site.

**MAS**: O bundle JS contem o path sem cache-bust. Se o browser cacheou a
imagem antiga em `/images/covers/castlevania.jpg`, e o bundle nao tem `?v=`,
o browser mostra a versao cacheada.

### Investigation Date: 2026-11-18

### 1. POST `/api/collections/:slug/cover` (server.ts:374-406) — CORRECT

The upload endpoint works correctly:

- **Line 391-392**: Writes processed image to `COVERS_DIR/<slug>.jpg` (which resolves to `public/images/covers/<slug>.jpg`).
- **Line 394-399**: Updates `collections.json` with a CLEAN path (`/images/covers/<slug>.jpg`) — no `?v=` cache-bust in persisted data. This is correct.
- **Line 402**: Calls `gitPersist("Atualizar capa: <slug>")` after saving both the image file and the JSON.
- **Line 404-405**: Returns response with cache-bust `?v=mtime` for immediate admin UI use.

**Verdict**: No bug here. The upload pipeline correctly writes the image, updates JSON with a clean path, and triggers git-persist.

### 2. PUT `/api/collections/:slug` (server.ts:337-363) — NO IMAGE CORRUPTION

The edit endpoint only updates fields that are explicitly sent in the request body:

- **Line 353-360**: Uses `if (body.X !== undefined)` guards for each field: `name`, `description`, `cardCount`, `moxfieldUrl`, `deckcheckUrl`, `hidden`, `sampleImages`.
- **Critically**: There is NO `if (body.image !== undefined) col.image = body.image;` line. The `image` field is never touched by PUT.
- **Admin UI saveCollection() (index.html:1847-1851)**: The PUT body contains only `{ name, description, cardCount, deckcheckUrl, moxfieldUrl }` — no `image` field is sent.
- **Admin UI toggleCollectionVisibility (index.html:1887-1891)**: Sends only `{ hidden: newHidden }` — no `image` field.

**Verdict**: The PUT endpoint cannot corrupt the `image` field. It simply does not touch it.

### 3. GET `/api/collections` (server.ts:260-277) — CACHE-BUST IS SERVE-TIME ONLY

- **Line 262-267**: Reads `collections.json`, then for each collection mutates `col.image` in-memory by appending `?v=<mtime>`. This is done on the in-memory copy returned to the client, NOT written back to disk.
- **Line 268-275**: Same pattern for `sampleImages`.
- Uses `readJson()` which reads fresh from disk each time, so the persisted JSON is never polluted with cache-bust params.

**Verdict**: Correct. Cache-bust is serve-time only and does not leak into persisted data.

### 4. git-persist (git-persist.ts:63-70) — INCLUDES COVER IMAGES

`FILES_TO_ADD` array includes:
- `src/data/collections.json`
- `src/data/testimonials.json`
- `src/data/settings.json`
- `public/images/covers/` (directory — stages all files inside)
- `public/images/decks/`
- `public/manuals/`

**Verdict**: Cover images are correctly included in the git-persist pipeline. Both the updated JSON and the new cover image file will be staged and committed.

### 5. Admin UI uploadCover() (index.html:1928-1980) — CORRECT

- **Line 1950-1953**: POSTs FormData to `/api/collections/<slug>/cover`.
- **Line 1962**: After success, calls `loadCollections()` which does GET `/api/collections` — this returns images with `?v=mtime` cache-bust.
- **Line 1964-1970**: Updates the preview image `src` to `col.image` (which now includes cache-bust from the GET response).

**Verdict**: Admin UI correctly shows updated cover because it re-fetches from the API which serves from `public/` with cache-bust.

### 6. Key Finding — Root Cause Confirmed

The upload pipeline, JSON persistence, and git-persist are all working correctly. The bug is NOT in any of these components.

The root cause is what F16-README hypothesized:

1. **Data baked at build time**: `store-data.ts` imports `collections.json` statically. The Vite bundle in `dist/` contains whatever data existed at build time. Even after admin updates `collections.json` and git-persist pushes + triggers a rebuild, the NEW build correctly picks up the updated JSON. However, the **image path in the bundle has no cache-bust** (`/images/covers/castlevania.jpg`), so browsers and CDN may serve the old cached image.

2. **The mismatch reported** (Castlevania showing cavaleiros-do-zodiaco image) suggests the JSON itself had wrong slug-to-image mapping at some point — this is a data issue in `collections.json`, not a code bug. T01 should have diagnosed this.
